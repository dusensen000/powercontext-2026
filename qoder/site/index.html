解决什么

进度要反复确认

「登录接口 P95 还没到 400ms」在启动会、周会、交接会被说了三次，措辞每次不一样。 人工对齐只能靠通读聊天记录，而且读一遍就会过时。

交接全靠嘴

人一调走，「旧 auth 接口不能下线，因为移动端 3.2 还在用」这类约束就留在历史消息里。 接手的人不知道有这条约束，一旦下线就是事故。

超期和失联没人管

任务散在纪要里，没有基准日，也就没人发现「原定 9 月 18 日联系 DBA」其实已经超期两周。

核心链路

  1. 粘贴纪要原始 Markdown 或聊天导出
  2. StepFun 抽取决定 / 行动项 / 风险 / 待确认，带负责人、截止日、状态
  3. seekdb 混合检索全文 + 向量 + 标量一次调用，RRF 召回候选，再复核余弦距离
  4. 合并入库同一件事更新状态，不同事才新增
  5. 对账按基准日算超期，按负责人算失联
  6. PowerContext 交接工作契约、Prepared Handoff、确认回执、任务结果

去重阈值是量出来的，不是猜的

RRF 分不能当相似度用，所以流程是「混合检索召回候选 → 本地 bge 向量复核余弦距离」。 三份纪要跑下来，距离分布分成两簇，中间是空的：

另外两个 seekdb 细节

namespace 与标量过滤
同一套库承载多项目：查询时带 {"project": "Aurora"} 与 {"status": {"$in": [...]}}，去重只在同项目、未完成的任务里比。

嵌入式跑在 WSL
seekdb 没有 Windows 原生包，用 pyseekdb 嵌入式实例； 数据目录放 WSL 文件系统，避开 /mnt/c 的文件锁。SEEKDB_HOST 一填即切 server 模式。

为什么这里必须是 PowerContext

台账解决「现在有哪些事」，解决不了「为什么这么定」。约束必须活得比单次会话久， 而且交接必须可确认——不能是「我口头交代过了」。

1Source

三份纪要原文落库，条目可回溯到原文位置

2Memory

决定与约束写成 atomic-memory，交接时自动召回

3Work Contract

目标、在范围、排除项、完成标准、未确认问题：position=44

4Prepared Handoff

当前状态 + 下一步，逐条带证据引用：position=45

5确认回执

接手人自检（现场/能力/授权）后 accept，证据状态 available

6Task Outcome

本轮结果与剩余工作落库：position=47

三个 position 取自 evidence/03-demo-e2e.log 那次运行； PowerContext 的位置在同一 Scope 内单调递增，每跑一轮演示都会往后走。

交接时 PowerContext 召回的上下文（/v1/context/prepare，2036 字节，节选自 evidence/04-powercontext-setup.log）

旧接口不下线约束：因移动端3.2版本仍在使用旧auth接口，该接口暂不能下线
登录接口P95性能目标：当前20%灰度下登录接口P95为520ms，距离400ms的目标仍有差距

每条都带 artifact_id + revision 引用，可回溯到原文；接手人不必重读三次纪要。

说清楚边界：本地未给 PowerContext 配推理模型，memory/search 走的是 mode=text 的词面召回；配上 embedding 后会切到语义模式。这一点在界面侧栏也会如实显示。

怎么复现

依赖选型

  • 对话模型：比赛发放的 StepFun step-3.5-flash（只提供对话，无 embedding 接口）
  • 向量：fastembed + BAAI/bge-small-zh-v1.5，ONNX 运行时，512 维， 完全不装 torch（此前 sentence-transformers 会拉 1.8GB CUDA 包并反复断流）
  • 模型下载：HF_ENDPOINT=https://hf-mirror.com，WSL 内访问不到 huggingface.co
  • 数据库：seekdb 嵌入式（pyseekdb 1.4.0），PowerContext 用独立 venv 避免依赖冲突

命令

# WSL：起 PowerContext Server
python3.12 -m venv ~/pc-venv
~/pc-venv/bin/pip install "powercontext[cli,server]==1.4.1"
mkdir -p ~/pc-run && cd ~/pc-run
~/pc-venv/bin/powercontext config init --template -o .env
~/pc-venv/bin/powercontext server run

# Windows：跑链路
bash run.sh scripts/smoke_embed.py
bash run.sh scripts/smoke_seekdb.py
bash run.sh scripts/demo_e2e.py --reset
bash run.sh scripts/setup_powercontext.py
bash run.sh scripts/retrieval_check.py
bash run.sh --ui        # http://localhost:8501

四条链路的原始输出都留在仓库 evidence/ 里（seekdb 三路对比、真实台账检索、 端到端逐条判定与交接卡、PowerContext 建 Scope 与召回），页面上每个数字都能在那几份日志里找到对应行。 开发全程使用 Qoder：链路设计、seekdb / PowerContext 接口核对（对着运行中服务的 /openapi.json 而不是猜字段）、WSL 环境排障、阈值校准与界面实现。 API Key 与 seekdb 数据不进仓库，只留在 .env（已在 .gitignore）。
